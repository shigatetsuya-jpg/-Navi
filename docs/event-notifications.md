# イベント通知の実装と公開条件

2026年11月7日。開発枝で検証済み、本番未反映・実送信未実施。

## 利用者ができること

`/notifications.html`で、メール確認済み会員が次を個別に保存できる。

- 団体が新しく公開したイベントのお知らせ。
- 選んだイベントの開催前のお知らせ。
- 選んだイベントの申込締切前のお知らせ。

すべて初期オフ。お気に入りから自動登録しない。登録時のメール宛てに送ることをチェック欄に表示し、設定の種類・時刻・同意版を保存する。個別停止・一括停止が可能で、非公開や終了後の対象も設定一覧から停止できる。認証・再設定・サイト内申込結果のメールとは別設定。

開催前と締切前は各24時間前から1回という初期値を実装。これは時刻の運用仮説。24時間以内に希望すると次回処理時に通知対象となる。新着は初回公開後24時間以内、かつ開催前・締切前だけ。過去イベントの一括配信はしない。申込締切後でも開催前なら開催リマインドを利用でき、案内先には締切済みと表示する。

外部フォームの申込有無・予約完了・残席を取得しない。本文にもイベント案内であることを明記する。外部サイトへ会員情報を自動入力・送信しない。

## 動作

- `006-event-notifications.sql`で初回公開日時、団体ごとの希望、イベントごとの希望、配信の一意記録を追加。旧データと待機メールを保存したまま更新する。
- 既存の公開中イベントは移行時刻を初回公開として記録する。この時点で購読設定は存在せず、移行だけで通知を作らない。旧イベントの実際の初回公開日が復元されたという意味ではない。
- 初回公開日は受付開始時に記録し、編集・終了・再公開でリセットしない。
- `scripts/event-notification-plan.mjs`で対象時刻を判定し、`scripts/event-notifications.mjs`で希望と現在の状態を照合する。
- 起動時と60秒ごとに、最大200件を既存の送信待ちテーブルへ登録。利用者・イベント・通知種類の一意記録も同じトランザクションで保存する。
- 既存の15秒ごとの送信処理に接続。送信直前に希望、本人のメール確認、現在の宛先、公開状態、開催・締切を再確認する。古い内容のまま送らず、最新のタイトル・日時・場所を用いる。
- 停止した待機通知は無効化し、重複防止記録は残す。再度オンにしても同じ種類を再送しない。停止済みでも送信処理へすでに渡したものの回収は保証できない。
- 退会は購読・リマインド・重複防止記録も連動削除する。送信待ちIDは再利用せず、退会で削除した末尾IDを次のメールの識別子に使わない。
- `EMAIL_DELIVERY_DISABLED=1`または送信元未設定では定期処理も配信も実行せず、希望だけ保存できる。画面は準備中と表示する。

現行の単一Webプロセス・永続SQLiteに合わせて実装し、新しいRender Worker/Cron、有料サービスは作っていない。厳密な配信時刻や全利用者への到達を保証するものではない。候補走査は小規模な初期運用向けで、利用拡大前に負荷と処理遅延を計測する。

## 検証

自動テストは希望の分離、未確認者の除外、期限切れ、非公開・退会・停止、最新内容、原子性と再試行、再起動・再公開後の重複防止、移行時の待機メール保存を確認。テスト専用の配送で公開イベントの自動通知を確認し、外部ホストへ送っていない。ブラウザは390px/1280pxで設定・再読込・個別/一括停止・非公開対象の停止、横はみ出しがないことを確認。

## 公開前に残ること

1. TSが規約・プライバシーの保存期間、委託先、問い合わせ対応と正式文面を確認する。
2. ドメインの購入価格・更新価格を提示して購入承認を得る。送信元DNSとメール事業者の設定、実送信・到達テストも承認後。
3. 先行PRとの依存、本番バックアップ・復元、旧会員の確認手順をレビューし、公開反映を明示承認する。
4. 復元時はメールを止め、バックアップ時点より後の配信記録との差分を照合してから再開する。復元で配信記録を巻き戻すと同じ通知を再び送る可能性がある。
5. メール事業者の障害・恒久失敗・停止中に通知の対象期間が過ぎる場合は配信されない。運営による監視・失敗確認と、負荷に応じた処理方式の見直しを行う。
