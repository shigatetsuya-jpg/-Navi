# サークルへの使用交渉で説明すること（未送信案）

関連：T06、T13、T14、T15。交渉するのはユーザー。ここには実施済みの協力・許諾・実績を記載しない。

## 目的と最初の依頼
新入生が活動時間・費用・参加条件から団体を探し、体験会へ申し込めるかを確認する。最初はユーザーが相談しやすい2〜3団体を優先する仮案。大学資料で見つけた団体より、既につながりがあり確認・修正が早い相手を優先する。

お願いしたいことは、掲載内容の確認、体験会1件の作成、試用申込の確認・判断、短い感想の提供。初回は合成アカウント・合成申込で操作を確認し、実際の学生を受け付ける前に情報共有と運用条件を確定する。参加を強制せず、協力の可否を確認する。

## 見せるデモ（約10分は仮説）
1. 学生画面：活動条件で探し、団体情報・体験会を見る。
2. 団体画面：イベントの下書き、運営確認後の受付開始、申込の確認と判断。
3. 学生画面：申込状態と取消。
4. 誰が申込情報を見られるか、困った時の連絡先、未提供の機能を説明する。

## 事前に合意する項目
- 試用期間：2週間を仮案とし、相手の都合を確認して決める。
- 料金：現時点で未確定。無料試用とするかをユーザーが決め、将来の有料化と混同しない形で明示する。勝手に課金しない。
- 掲載範囲：名称・紹介・活動条件・イベント・公式リンクのうち相手が確認した内容だけ。運営者の公開承認も必要。
- 実際の学生を募集するか、操作検証だけかを明確にする。申込情報を扱う担当者を決める。
- 通知：実メールを使う場合は検証・外部送信の承認後。通知なしなら、団体が画面を確認する頻度と担当を合意する。
- 問い合わせ：運営者名・窓口・対応可能時間を確定する。大学公認サービスとは説明しない。
- 終了・撤回：掲載停止、データ訂正、アカウントや試用データの取扱いを明示する。

## 評価と次への判断
登録→イベント作成→申込確認で止まった場所、申込状況が理解できたか、運営の手間が減るかを確認する。架空の申込を利用者獲得KPIへ含めない。協力団体数・実申込数・実参加数を別に管理し、外部に実績を公表する前に根拠と許諾を確認する。
