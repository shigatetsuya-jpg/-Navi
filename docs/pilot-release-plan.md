# 試用版の反映・交渉開始プラン（承認待ち）

## 今回仕上げる試用の範囲
最初はユーザーが相談しやすい2〜3団体で、架空の学生情報を使った操作確認を行う。試用期間2週間・利用料0円を提案する。正式な実学生向け受付や有料提供を開始した意味ではない。
メール通知はEMAIL_DELIVERY_DISABLED=1で明示的に停止し、学生はマイページ、団体は団体画面で状態を確認する。外部のメール送信は別途承認・到達確認後。試用中の確認頻度は開始時と各操作後とし、実受付に使う場合の頻度・担当者は別途合意する。

## 反映候補
- 既存の検索・登録・イベント・申込・判断・取消、定員・待機列。
- 管理者用実績集計、空結果・通信失敗からの案内。
- イベント保存後の画面更新、過去開催・締切済みイベントの受付候補からの除外。
- 通知用スキーマと所有確認（ただし送信無効）、DB更新前の自動コピー。
- 運営名・問い合わせ先・試用説明の公開表示は、ユーザーの表示内容承認後に反映する。実氏名・連絡先はこのリポジトリに保存しない。

## データの扱いと保持案
操作確認では合成データを使う。実アドレス・実名を入力する場合、それらをRenderへ送信することと見える範囲を説明して同意・承認を得る。申込の氏名・大学・学年・任意本文は担当団体に表示し、学生のメールは団体画面に返さない。運営者の管理画面ではアカウント情報を確認できる。
試用データは試用終了後30日以内に整理・削除する案。削除前に対象と他の利用者への影響を確認し、ユーザーの明示承認後に実施する。本番バックアップの保持・退避と関連ログは別管理であり、即時の完全削除とは説明しない。実データ受付前に保持範囲・実施日を確定する。

## 反映前チェック
1. このプラン、0円・2週間・通知なしの限定試用、運営表示をユーザーに承認してもらう。
2. 現在のRenderサービスと接続ブランチ・稼働版を再照合し、メール送信停止を適用する。DBのマウント先と保存先が一致することを取得可能な範囲で確認する。
3. 後続のPR #4をPR #3のブランチに統合し、修復込みの最終版で全自動テストとブラウザの一連の操作を再実行する。未修復のPR #2だけを先に本番へ入れない。
4. 本番枝の変更は1回にまとめる。新インスタンスの起動時にDBコピーを作り、検査成功後にスキーマと版番号を同じトランザクションで更新。保存や検査に失敗したら起動を中断する。
5. Renderのliveだけでなく、health、検索、ログイン画面、未認証管理APIの拒否を確認。実データを伴う登録・公開のテストは承認範囲で行う。
6. 全体結果・未提供機能・デモ手順を報告し、ユーザーへ交渉開始の合図を出す。

## データ保全の限界
自動コピーは永続ディスク内に作るため、ディスク自体の喪失には備えられない。外部退避・本番からの復元確認は未完了。初回の合成データによる操作試用と、実学生の申込を受ける本運用を区別する。実学生の受付前には外部保管と復元確認を済ませる。
障害時は新規書込みを止め、DB互換性を確認してから旧コードへ戻す。RenderのコードRollbackだけでDBは元に戻らない。スキーマ追加は既存列を残すが、実際に安全に戻せるかはリリース時の差分で確認する。

## 承認依頼に含めるもの
- 公開する運営者名・問い合わせ先の表示。
- 2週間・0円・メール通知なし・架空データ中心の少数団体試用。
- 本番への反映と公開される画面・イベント候補の変更。
営業送信、実団体の掲載、実メール、課金、有料契約、実学生の個人情報送信は一括で承認されたとは扱わず、別の対象と内容で確認する。
