# データ保全と通知の本番確認

## 現状
この文書とバックアップツールは準備済み。本番のDBを取得・変更していない。Render管理画面への認証済みアクセス、実際の保存設定、バックアップ取得と手元への転送は別途必要。

## Renderで確認する項目
- 対象サービスが navi-qzh7.onrender.com であること、接続ブランチと稼働コミット。
- Diskのマウント先とDB_PATHが一致し、DBがディスク配下にあること。
- 有料サービスと1GBディスク、その他の有料サービス・Workspaceの請求内訳。
- Search Consoleは別サービス。所有権確認ファイルがあることと検索登録完了は同じ意味ではない。

## 更新前のバックアップ
修正が入ったブランチを本番へ入れる前に、scripts/backup-db.mjsを作業用に用意する。Node.js 24で、DB_PATHを既存の設定のまま使い、Render Shell内で実行する例：

```sh
node scripts/backup-db.mjs /opt/render/project/src/data/backups/before-update-20261107.sqlite
```

同名ファイルが存在すると失敗するので、取得ごとに別名を指定する。稼働中SQLiteのWALも含めて整合したコピーを作り、整合性と外部キーを検査する。元DBを新規作成・上書きしない。バックアップは所有者だけが読める権限で保存する。

同じディスク内のコピーだけではディスク喪失に備えられない。Renderの認証済み転送手段（SSH/SFTPなど）で運営者の安全な保管場所へコピーし、ファイルサイズ・ハッシュと読み取り確認を行う。個人情報を含むため公開URL、GitHub、チャットには添付しない。

## 復元の確認
バックアップを別の作業環境へコピーし、外部送信の環境変数を外したうえで、コピーをDB_PATHに指定して起動する。管理者ログイン、団体・利用者・申込件数、申込状態を照合する。元のバックアップは直接起動に使わずコピーを使う。

本番復元時は申込等の書込みを止め、プロセスが停止した状態で現在のDBとWAL/SHMも退避してから、検証済みDBへ切り替える。稼働中にDBファイルだけをコピーして置換しない。復元時点より新しい操作が失われるため、対象時点と影響をユーザーと確認してから実施する。

## メール送信を有効にする前
1. 本番DBのバックアップと復元確認を行う。
2. Resendの送信元ドメイン・DNS、EMAIL_FROM、RESEND_API_KEYを確認。秘密値をGitHubへ保存しない。
3. PUBLIC_SITE_URLを実際のHTTPS公開先に設定し、リンクの遷移先を確認。
4. 検証環境・運営者の検証アドレスだけで、登録確認、再送、期限切れ、申込受付、団体への新着、承認・見送り、繰り上げを試す。
5. 到達・迷惑メール・失敗時の再試行と送信失敗の発見方法を確認。ローカルの代替送信テストは実メール到達の保証ではない。
6. 既存アカウントもメール確認が必要。ログイン後の案内と、確認前には申込ができなくなることを確認。

利用者別の通知オン・オフは未実装。通知設定を有効にしただけで実利用の準備完了とはしない。

## 今回のローカル検証
- 公開APIは公開・確認済みだけを返し、contactを含めない。
- 確認リンクは一度だけ有効。期限切れ・再送前の古いリンクは無効。
- 未確認者の申込拒否、再送回数制限。
- 定員超過は待機列へ、取消で繰り上げ。他団体は申込を閲覧・判断できない。
- 外部サービスを代替し、送信先、個人名・メッセージを載せないこと、503時の再試行予約、送信済みペイロード消去を確認。
- 古い送信待ち通知も、送信直前に宛先の確認状態を照合する。
- SQLiteバックアップからの読み出し、WAL内容、上書き拒否、元DBがない場合の失敗。

Chromiumでも、登録フォーム→確認待ち表示→再送→確認リンクの明示的な確認完了とURLからのトークン除去を確認。ブラウザ例外なし。送信はテスト用の代替処理。

本番の実設定、実メール到達、通知の包括的な負荷・障害試験は未確認。

## 更新前の自動コピー
通知用のスキーマ更新が必要な既存DBに対して、server.mjsは更新前に同じ保存先のbackupsディレクトリへ検証済みコピーを作る。コピー作成・検査に失敗したら起動を中断し、通知用のDB更新を行わない。新規DBには不要なコピーを作らない。これは同一ディスク内のコピーで、外部保管と復元確認は別途必要。
